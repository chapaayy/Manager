# XPPN Manager 2.3 — один центр управления Remnawave

Новая автономная кодовая база без VPN-проектов и нескольких панелей. Старый XPPN v1 не удаляется. Развёртывание на отдельном чистом VPS теперь можно **запустить из браузера**, но полноценное подключение на реальном VPS ещё требует эксплуатационного тестирования.

## Обновление установленного менеджера

Открой свой HTTPS-домен Manager → **Обновления → Проверить → Установить**. Веб-панель отправляет запрос отдельной root-owned службе: та сохраняет базу/секреты, обновляет фиксированную ветку GitHub, пересобирает контейнер, проверяет HTTP и пытается восстановить предыдущий код при ошибке. SSH-пароль VPS может храниться в базе только зашифрованно через XPPN_DATA_KEY; API и браузер получают только признак наличия пароля, но не его значение. Для первой настройки системы обновлений есть однократный скрипт v2/activate-web-updates.sh.

## Библиотека конфигураций и nodes-only режим

Активная система мостов временно **отключена**. На странице «Ноды» нет топологии, entry/exit-ролей, кнопки создания мостов и планов связей. Новые VPS создаются только как обычные самостоятельные ноды. Старые таблицы мостов в SQLite намеренно не удаляются при миграции, чтобы обновление Manager не было разрушительным; legacy HTTP-маршруты возвращают 410 и не применяют изменений.

Во вкладке **«Конфигурации»** Xray и серверные файлы хранятся отдельно. Для каждой ноды можно независимо выбрать Xray, Nginx, Nginx Compose и Remnawave Compose из библиотеки. **Сохранение выбора не применяет файл на VPS или в Remnawave** — это только явная привязка библиотеки к конкретной ноде. Фактический файл с VPS читается отдельно через Agent.

Для новой VPS остаётся один установочный тип — Direct VLESS TLS. Direct-пресет содержит Xray + Nginx + оба Compose-файла и используется только для первоначальной установки обычной ноды. Старый Bridge Xray-файл сохраняется как обычный файл библиотеки; Bridge-пресет больше не является установочным и переводится в library-only/custom без перезаписи его содержимого.

## Единое управление нодами и первый TLS-статус

В боковом меню теперь **одна вкладка «Ноды»**. Карточки серверов открывают полноширинное рабочее пространство конкретной VPS: обзор состояния и агента, Docker/службы, логи, TLS, конфигурации и действия управления. Прежние отдельные пункты меню «Агенты VPS» и «Сертификаты нод» убраны; их операции доступны внутри ноды. Технические команды остаются через существующий ограниченный HTTPS Agent, не через SSH.

После того как Remnawave подтвердила готовность новой ноды, менеджер **сразу ставит первую проверку сертификата в очередь агента**. Первый heartbeat готовой ноды также гарантирует постановку задания, если его ещё не было. Повторные heartbeat не дублируют уже поставленную проверку. Пока агент выполняет проверку, интерфейс сообщает «Проверяется»; срок действия и успешный статус показываются только после подтверждения агентом. Последующие проверки по-прежнему периодические, раз в 6 часов. Приватные ключи остаются только на VPS.

## Новые страницы

- **Конфигурации** — только полноширинный каталог файлов, поиск, отдельная кнопка создания. Просмотр и редактирование открываются в диалоговом окне.
- **Пресеты** — только каталог наборов, редактирование/создание в отдельном окне.
- **Ноды** — плоский список VPS и детальная страница каждой ноды с агентом, TLS, Docker, логами, независимым выбором конфигов и управлением.
- **Настройки** — одна Remnawave и глобальная частота мониторинга: **1 секунда** (диагностический быстрый режим) или **5 секунд** (обычный режим).
- **Обновления** — штатное обновление из веб-панели.

Если библиотека была пустой или неполной, добавляются **Direct Xray**, сохранённый legacy **Bridge Xray** как обычный library-only файл, `nginx.conf`, Nginx Compose и Remnawave Node Compose. Автоматически создаётся только Direct-пресет установки. Пользовательские правки и удалённые starter-файлы не перезаписываются при каждом старте.

## SSH Fail2Ban на существующей ноде без переустановки

В **Ноды → выбранная VPS → Сеть и защита** доступны компактные текущие показатели сети, проверка BBR/FQ, Firewall Node API 2222, ротации Nginx, SSH Fail2Ban, активных блокировок и последних `Ban/Unban` из журнала fail2ban.

**Для ранее установленной ноды:** сначала обнови Agent до **v1.5.0** через «Управление». Поскольку механизм автообновления Agent меняет только Go-бинарник, существующий root-helper нужно **один раз подготовить по явному подтверждению через SSH**. Ключ сервера сверяется с сохранённым fingerprint. Скрипт проверяет новые служебные файлы, создаёт резервную копию прежнего helper и не меняет токен, systemd-службу, Remnawave, Xray или Nginx. Новые чистые VPS получают этот helper сразу в установке.

После подготовки доступна отдельная кнопка **«Установить Fail2Ban для SSH»**. Необходимо вручную указать доверенный публичный IPv4, с которого администрируется SSH: он включается в `ignoreip` вместе с localhost и, если определён, адресом панели. Применение ограничено **только** SSH jail с `backend=systemd`: 6 неудачных попыток за 10 минут, блокировка на час. Изменения `sshd_config`, глобальной политики firewall, Docker или 2222 отсутствуют. Fail2Ban по назначению создаёт собственные правила временной блокировки SSH в системном firewall. Если Fail2Ban уже установлен посторонним способом, менеджер **не перезаписывает** его конфигурацию. При ошибке проверки jail новый XPPN конфиг удаляется, а результат виден на странице ноды.

Разблокировка IP выполняется только в SSH jail, только для адреса из списка текущих блокировок, с дополнительным подтверждением. Настройка идёт в отдельном systemd-задании: агент и VPN продолжают работать, состояние и причина отказа доступны при повторной проверке страницы. Данные журнала ограничены событиями `sshd Ban/Unban`, полный системный журнал не отображается.

Сетевой мониторинг показывает текущие RX/TX в бит/с, Кбит/с или Мбит/с (по величине) и общий объём в Б/КБ/МБ/ГБ; TCP retransmits и packet drops остаются накопительными счётчиками. **Не** включены Hysteria2, CAKE, shaping, дополнительные sysctl или High Load tuning.

## Быстрый Agent, мониторинг и обновления

Agent **v1.5.0** разделяет heartbeat мониторинга и очередь команд на два независимых цикла. Команды используют HTTPS long-poll: Agent держит открытый запрос примерно до 25 секунд, а Manager будит его сразу после постановки задания. Поэтому чтение логов и конфигов больше не зависит от прежнего 5-секундного polling sleep. В интерфейсе готовый результат задания проверяется каждые ~200 мс на первой стадии.

Heartbeat настраивается глобально в **Настройки → Мониторинг**:
- **1 секунда** — очень быстрый диагностический мониторинг;
- **5 секунд** — обычный режим.

Режим мониторинга не меняет частоту long-poll задач: логи, чтение конфигов, рестарты и другие действия доставляются независимо. В 1-секундном режиме Agent чаще обновляет системные показатели и RX/TX; Manager не выполняет тяжёлую TLS-проверку или проверку обновлений на каждом heartbeat.

В **Ноды → Управление → Обновления агента** остаются ручное обновление и opt-in автообновление. Бинарник скачивается только с авторизованного Manager, проверяется по SHA-256 и доверенному release manifest, а root watchdog возвращает предыдущий Agent, если новая версия не подтвердит HTTPS heartbeat. Автообновления распределяются между нодами, чтобы не перезапускать их одновременно.

## Минимальная безопасная настройка новой VPS

После **успешного запуска** Remnawave Node установщик запускает необязательный скрипт `v2/data/node-baseline.sh` **только на чистом VPS при новой установке**. Скрипт не редактирует SSH, Docker, конфиги Xray, действующую Remnawave и не меняет политику firewall. Ошибка дополнительной настройки не останавливает работающую VPN-ноду.

- **BBR/FQ:** только `net.ipv4.tcp_congestion_control=bbr` и `net.core.default_qdisc=fq` при поддержке ядра. Прежние значения сохраняются в root-only файле `/etc/xppn-baseline-previous`; проверка результата и попытка отката при ошибке. Не перезапускаются интерфейсы и действующие соединения. Дополнительный TCP tuning не применяется.
- **Fail2Ban:** только `sshd` с `backend=systemd`, 6 попытками за 10 минут, баном на 1 час. SSH-порт берётся из `sshd -T`, текущий IP установочного SSH-сеанса и IP панели исключаются из блокировок. При неизвестном IP администратора или существующем Fail2Ban автоматическое управление пропускается. Проверяется `fail2ban-client -t` и состояние `sshd`; при ошибке созданная конфигурация удаляется. Nginx и VPN-клиенты не банятся.
- **Firewall:** неизменен. Остаётся ранее установленное ограничение доступа к API Node 2222 по IP Remnawave. Никаких `ufw enable`, глобальных DROP, переписывания Docker или правил SSH.
- **Логи:** отдельная ротация Nginx, не затрагивающая существующие Docker/Xray logrotate; 7 архивов, 20 МБ.
- **Мониторинг:** Agent v1.5.0 сообщает счётчики сети через обычный heartbeat, без дополнительного открытого порта. На странице ноды «Сеть и защита» можно выполнить **только чтение** текущих BBR/FQ, Fail2Ban/SSH jail, управляемого правила 2222 и ротации. Скорость RX/TX рассчитывается по разнице двух замеров на активном интерфейсе; bytes, retransmits и drops **накопительные**, их нельзя считать скоростью или процентом потерь.

Уже установленные VPS не изменяются обновлением Manager. Для диагностики новой функции на старых нодах потребуется отдельное безопасное обновление Agent; его нельзя подменять SSH-операциями без подтверждения. Проводить тесты изменений сети сначала на чистой RUS10, а не на рабочих нодах.

## Удаление нод без очистки VPS

**Ноды → Управление** теперь открывает удаление только из Manager и/или через Remnawave API. SSH, Agent, Docker, Nginx, Certbot и сама VPS не затрагиваются. Поддерживаются варианты:

- удалить только запись из Manager (регистрация в Remnawave остаётся);
- удалить ноду из Remnawave и Manager, сохранив профиль;
- удалить ноду из Remnawave, её отдельный Manager-owned Xray Config Profile и запись в Manager.

Менеджер сначала проверяет UUID и привязки через API. Если профиль общий, он перечисляет другие ноды, по умолчанию сохраняет профиль и требует ввода точного названия плюс отдельного подтверждения для удаления общего профиля. Важно: удаление общего профиля может нарушить VPN-подключения **других нод** — панель их настройки автоматически не исправляет. Если имя профиля изменилось или назначение ноды нельзя проверить, автоматическое удаление профиля блокируется.

Сбой API оставляет локальную запись для повторной попытки. Стадия прежнего удаления `finalize_ack` завершается новым способом без повторной отправки команд VPS. Старые HTTP-маршруты полного удаления VPS отключены (410); при запуске менеджера ранее поставленные в очередь задания очистки отменяются. Задания, уже выполняющиеся на удалённом агенте, автоматически остановить нельзя — их состояние следует проверить отдельно.

## Первый VPS: реальная установка

Кнопка **Ноды → Добавить VPS** устанавливает только обычную Direct-ноду:

1. Код/название, страна, IPv4 VPS, SSH-порт, домен, root-пароль и исходящий IPv4 Remnawave.
2. До любых изменений Manager проверяет SSH, host fingerprint, root, ОС, DNS, свободное место, нужные порты и отсутствие конфликтующей установки.
3. После подтверждения на чистой VPS устанавливаются Docker/Compose, Certbot, Nginx fallback, Remnawave Node, firewall для TCP/2222 и базовая безопасная настройка.
4. Создаётся отдельный Direct Xray Config Profile и нода регистрируется через Remnawave API.
5. Пароль root сохраняется в Manager **зашифрованно** и дальше используется только для явно подтверждённых SSH-операций, которым SSH действительно нужен. Страница ноды показывает IP/порт/fingerprint и только факт наличия сохранённого пароля; сам пароль через API не возвращается. Его можно заменить или удалить.
6. Выбранные при установке файлы записываются как независимые config choices ноды; дальнейшая смена выбора не применяет конфиг автоматически.

Входные/выходные роли мостов и создание topology в этом релизе отключены. При ошибке удалённой установки автоматический rollback всей VPS по-прежнему не гарантируется, поэтому первую проверку новых установочных изменений проводить на тестовой VPS.

## Файлы проекта

- v2/app.py, v2/storage.py — API, одна SQLite база и статусы.
- v2/remnawave.py — HTTPS API адаптер к единственной Remnawave.
- v2/template_engine.py — проверка и безопасный рендеринг Xray-шаблонов; legacy bridge-утилиты не используются активным UI.
- v2/vps_install.py, v2/data/remote-install.sh — SSH проверка, supervised bootstrap, Nginx/TLS/Node, создание профиля.
- v2/bundled.py, v2/library.py — образцы, пресеты и зашифрованная библиотека.
- v2/static/ — новый интерфейс и мастер VPS.
- tests_v2/ — тесты генерации, авторизации, базы, сценариев обновления и установщика (без обращения к настоящим серверам).

## Обновление с v1

Перезапись прежней SQLite/сервисов v1 запрещена. Для переноса только одной Remnawave есть read-only мигратор v2/migrate.py, старые ноды не переносятся. Домен, ключи и учётные данные v2 сохраняются при обновлениях.
